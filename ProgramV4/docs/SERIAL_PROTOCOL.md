# シリアル通信プロトコル (上位 ⇄ MD)

上位の車両制御基板 (STM32F446RE) と、このモータドライバ (MD, STM32F303K8) の間の通信仕様。

- **UART 1000000 bps, 8N1** (USART2。250000 bps から変更したので、上位側と必ず同時に合わせること)
- 多バイト値はすべて**ビッグエンディアン**
- 両方向ともフッタは無く、末尾は **CRC-8** のみ
- 上位は制御周期ごと (**2 kHz**) に指令フレームを送り、MD は **2 kHz** (`SERIAL_SEND_INTERVAL_US`) で状態フレームを返す
- 1 Mbps では指令フレームが 60 us、状態フレームが 110 us (回線の2割強)。250000 bps では状態フレームだけで
  440 us かかって 9 割近くを占めるので、周期とボーレートはセットで決める

## CRC-8/AUTOSAR

```
poly = 0x2F, init = 0xFF, xorout = 0xFF, 入出力のビット反転なし
```

AUTOSAR CRC ライブラリの `Crc_CalculateCRC8H2F` と同一。
**チェック値**: `"123456789"` (`0x31`〜`0x39` の 9 バイト) に対して **`0xDF`**。

計算対象は「**先頭の `0xAA` を除き、CRC 自身の手前まで**」。

### なぜフッタでは駄目だったか

ヘッダ `0xAA` + 固定フッタ `0xFF` では、検出できるのはフレーム長のずれだけで**ペイロードのビット化けは検出できない**。
データ部にも `0xAA` / `0xFF` が現れうるため、バイト落ちで同期がずれると、偶然位置の合った値を頭と尻だと誤認して
デタラメな値を制御に入れてしまう。

`0x2F` は AUTOSAR が車載通信向けに選んだ多項式で、このフレーム長なら **2ビットまでの化けは必ず検出**する
(テストで 1ビット 40通り・2ビット 780通りすべての棄却を確認済み)。

## 受信フレーム (上位 → MD): 6 バイト固定長

| オフセット | 内容 | 型 | 備考 |
|---|---|---|---|
| 0 | `0xAA` | u8 | ヘッダ |
| 1 | mode | u8 | 下表 |
| 2–3 | setpoint | **i16** BE | スケールは mode ごと |
| 4 | torque_limit | **u8** | × 0.001 → 0〜0.255 N・m |
| 5 | crc8 | u8 | byte1–4 に対する CRC-8 |

テストベクタ: `AA BB 01 F4 32 26` (位置指令 0.500 rad / トルク上限 0.050 N・m)

### mode とスケール

| header | モード | スケール | 単位 | i16 レンジ |
|---|---|---|---|---|
| `0xBA` | 角速度指令 | 0.01 | rad/s | ±327.67 |
| `0xBB` | 位置指令 | 0.001 | rad | ±32.767 |
| `0xBC` | トルク指令 (Iq) | 0.001 | A | ±32.767 |
| `0xBD` | トルク指令 | 0.0001 | N・m | ±3.2767 |
| `0xBE` | 制動電流指令 | 0.001 | A | ±32.767 |
| `0xBF` | 制動トルク指令 | 0.0001 | N・m | ±3.2767 |

表の実体は app.c の `SERIAL_COMMANDS`。モードを増やすときはここに1行足す。

## 送信フレーム (MD → 上位): 11 バイト固定長

| オフセット | 内容 | 型 | スケール |
|---|---|---|---|
| 0 | `0xAA` | u8 | ヘッダ |
| 1 | status | u8 | bit4:エンコーダ未校正 bit3:過電流 bit2:過熱 bit1:電源電圧異常 bit0:指令あり |
| 2 | temperature | u8 | 1 degC |
| 3–4 | theta | **u16** BE | 0.0001 rad (0.1 mrad) |
| 5–6 | speed | **i16** BE | 0.01 rad/s |
| 7–8 | iq | **i16** BE | 0.001 A (1 mA) |
| 9 | torque_limit | **u8** | × 0.001 N・m — **適用中**の値 |
| 10 | crc8 | u8 | byte1–9 に対する CRC-8 |

byte 9 は**受信値そのままではなく、MD が実際に適用している値**。
上位から「本当に効いている制限」が見えることに意味がある。

status のビット (`serial_protocol.h` の `SERIAL_STATUS_BIT_*`):

- bit0 **指令あり**: 受理済みの指令を実行中 (停止モードでない)。「回転中」ではない。
  無通信タイムアウト・異常中は 0。
- bit1〜3: 異常 (1 = 異常)。**異常中も状態フレームは通常の周期 (2kHz) で返し続ける**
  (2026-10 まではLED点滅の待ちで約1Hzに落ちていた)。異常中は指令を受け取らず、
  byte 9 の制限値も 0 を返す。復帰したときは、異常の前後に届いていた指令をすべて捨て、
  新しいフレームを受け取るまで動かない。
- bit4 **エンコーダ未校正** (2026-10 追加): フラッシュの校正値が無効。この間は制限値を
  受け付けず (byte 9 は常に 0)、モータは動かない。スイッチを押しながら起動して校正する。

テストベクタ: `AA 09 2A 27 10 FB 2E 09 C4 32 7C`

## 制限値をなぜ毎フレームに載せるのか

設定コマンドとして別送するのではなく、**毎回の指令フレームに載せる** (CANopen の
RxPDO 相当)。フレーム 1 つが常に完結した状態を表すので、

- 取りこぼしても次のフレームで復元される
- MD がリセットしても次のフレームで復元される
- 「設定値の同期がずれる」という問題自体が発生しない

## 制限値の適用

### MD 側の絶対上限

上位が送ってきた値を MD が無条件に信じてはいけない。上位のバグや設定ミスがそのまま
モータと FET の破壊につながる。実際に適用するのは**受信値と MD 側の上限の小さい方**。

| | MD 側の上限 | 定義場所 |
|---|---|---|
| トルク | `Kt × MAX_CURRENT` (Kt は校正した ψm から実行時に計算) | config.h + 校正値 |

**上位が指定できる制限はトルクだけ。** 速度は上位のモーションコントローラが指令値
そのもので決めるべきもので、MD 側にもう一段の速度飽和を置くと同じ量を 2 箇所で作る
ことになる。MD が持つべきなのは「モータと FET を焼かないための電流の天井」だけ。

速度側には `MAX_ANGULAR_SPEED = 150 rad/s` が**速度モードの指令をクランプする MD 固定の
ハード保護**として残っている。上位から変えられない (変えられてはいけない) ので通信には
載せない。位置モード・トルクモード・制動モードには速度の頭打ちが一切無く、
物理的な天井 (逆起電力が母線電圧に追いつく約 406 rad/s) まで回りうる。

**比較はバイト表現のまま行う** (`ApplyLimits`)。float にして min を取ると丸めで 1LSB ずれ、
「20 を送ったのに 19 が返ってきた」となって制限か通信化けか区別できなくなる。

#### u8 のスケールをどう決めたか

`torque_limit` は u8 なので、**スケールは「最大トルク / 255」以上でなければ上限指定が
モータの全域に届かない**。一方でスケールが大きすぎると刻みが粗くなる。

| スケール | u8 レンジ | 分解能 | 0.1947 N・m 内の段階数 | |
|---|---|---|---|---|
| 0.01 | 0〜2.55 N・m | 10 mN・m | **19** | 粗すぎ。レンジは 13 倍余る |
| **0.001** | 0〜0.255 N・m | 1 mN・m | **194** | 天井はモータ最大の 1.31 倍。適切 |
| 0.0001 | 0〜0.0255 N・m | 0.1 mN・m | — | **最大トルクに届かない** ✗ |

このスケールの天井 0.255 N・m は `MAX_CURRENT` に直すと **13.1 A 相当**。
`MAX_CURRENT` をそれ以上に上げるなら、スケールを見直さないと上位から上限を指定しきれない。

**指令側 (`0xBD`/`0xBF` の i16、0.0001 N・m) は細かくしない。** 電流センサの量子化
`0.0081 A/LSB × Kt 0.01947 N・m/A = 0.158 mN・m` より、現行の 0.1 mN・m 刻みが既に細かいため。

### 起動直後は 0 = 動かない

**「0 = 無制限」と解釈してはいけない。** フェイルオープンになり、通信失敗が全力回転に
つながる。制限値を受け取れていない状態でモータが回らないのが正しい挙動。

無通信 0.5 秒のタイムアウトでも制限値を 0 に戻す。通信が切れた後で再開するときは、
必ず新しい制限値を受け取ってから動き出す (起動直後と同じ状態にそろえる)。

校正 (スイッチを押しながら起動) だけは通信より前に走るので、`BLDC_MeasureSteadyPoint` が
一時的に MD 側の絶対上限まで開け、`BLDC_Init` の最後で 0 に戻している。

### torque_limit — トルク (電流) 指令の飽和値

`BLDC_OuterLoop` が毎周期 `speed_pid.output_limit` と `position_pid.output_limit` に
入れる。`BLDC_PIDControl` のアンチワインドアップ (バックカリキュレーション) はこの
`output_limit` を基準に働くので、**飽和中は積分が伸びない**が自動的に成立する。

PID を通らないトルクモード・制動モードにも効かせるため、外側ループの最後で
モードによらず `target_iq` を `±iq_limit` でクランプする。

### 位置モードには速度制限もランプも無い

位置制御は目標角との偏差 (`FOC_AngleDiff` で ±π) をそのまま PID に入れ、出力を `±torque_limit` で飽和させる素の構成。

```
目標角度 ──▶ [位置PID] ──▶ clamp(±torque_limit) ──▶ Iq指令
```

以前は位置指令のランプを speed_limit の速さで動かし、実位置から離れすぎないよう引き戻していた。
speed_limit を廃止するとこの機構は成立せず (ランプが即座に目標へ飛び、引き戻しが毎周期効いて出力が `kp × 引き戻し幅` の定数になる)、
torque_limit が効かないモータになったためランプごと撤廃した。

- **拘束中の保持電流は torque_limit そのもの** (ホスト検証: 0.10 N・m で 5.13 A)。ラックエンドに当て続けると
  上限いっぱいの電流が流れ続けるので、「焼かない電流」を選ぶ責任は上位にある
- 拘束を解いた後の行き過ぎは邪魔されない普通の移動と同程度 (0.32 rad)
- ワインドアップは `BLDC_PIDControl` のバックカリキュレーションが抑える

### 移動速度は何が決めるのか

位置モードの移動速度は **torque_limit と負荷と PID ゲインの合成**で決まる。加速側は torque_limit が支配し
(`a = Kt·iq_limit / J`)、減速側は飽和から抜けたあと `ω ≒ (kp/kd)·error` の包絡線に乗る。
ホスト検証 (`tests/test_limits.c`、J=3e-5, B=2e-4, torque_limit 0.10 N・m) の速度ピークは
移動量 0.5 / 1.5 / 3.0 rad で 12 / 46 / 91 rad/s (トルク律速の上界 41 / 71 / 100)。

**速すぎるときに戻すのは `kd`** (上げると減速の包絡線が寝る)。torque_limit を下げると加速側だけが鈍る。

## DMA の使い方 (遅延に直結する)

- **受信**: 循環 DMA。受信位置は DMA の残り転送数 (CNDTR) から毎回読み、周回数だけを満了割り込みで
  数える (`lib/serial/serial.h`)。半分/満了割り込みでしか進めないと、256 バイトのバッファでは
  指令約 21 ms ぶん溜まるまで受信が見えない。
- **送信**: **Normal** DMA。Circular だと同じバッファを再送し続け、`SendSerial` の上書きで中身が
  入れ替わったフレームが CRC 不一致で捨てられる。USART2 の NVIC 割り込みは有効にしていないので、
  `Serial_Write` は毎回 `HAL_UART_AbortTransmit` で gState を戻してから送る。

## 指令の反映

トルク (`0xBC`/`0xBD`)・制動 (`0xBE`/`0xBF`) モードは PID を通らず指令を素通しするだけなので、
1 kHz の外側ループを待たず **20 kHz の電流ループで毎周期** Iq 指令へ反映する
(`BLDC_DirectIqLoop`)。制動の向きを決める `tanh` の係数だけは速度依存なので 1 kHz で更新する。
速度・位置モードは従来どおり 1 kHz。

## 受信の状態機械と再同期

1. 先頭は必ず `0xAA`。違えばそのバイトを捨てて次を待つ
2. `SERIAL_RX_FRAME_SIZE` (6) バイト溜まったら CRC を検査する
3. 合えば適用し、`serial_recv_timer` をリセット (緑 LED 点灯)
4. **合わなければ破棄し、前回の指令値と制限値をそのまま保持する。**
   誤った値で制御するより 1 周期古い正しい値を使う方が安全
5. 破棄したときは、**バッファ内の次の `0xAA` を先頭に詰め直す**

手順 5 が再同期の肝。単に長さを 0 に戻すと、捨てたバッファの中にあった本物の
ヘッダごと捨ててしまい、復帰が 1 フレーム余計に遅れる。詰め直せば本物のフレーム
境界を 1 バイトも読み飛ばさずに拾い直せる (テストで「1 バイト欠落 → 次のフレームで
復帰」を確認済み)。

**モードが変わるのは CRC が通ったフレームだけ** (ノイズの 1 バイトでモードが切り替わらない)。

### 破棄カウンタ

`rx_crc_error_count` (CRC 不一致) と `rx_unknown_mode_count` (CRC は合ったが未知の
モードヘッダ) を持つ。`config.h` の `STATUS_PRINT_INTERVAL_S` を 0 以外にすると
状態表示に `crcerr:` / `mode?:` として出る。

### 無通信 0.5 秒での停止

`SERIAL_TIMEOUT_S`。通信断 (断線・上位のハング) の保険。この時間は直前の指令を出し続ける
ので、**上位は止める手段として使わないこと** (止めたいときはトルク 0 か制動を明示的に送る。
上位の車両制御基板は 2026-10 にそうした)。

### メインループのウォッチドッグ

指令の受信・無通信タイムアウト・異常の監視はメインループにあり、20kHz の制御ループは
割り込みで回る。メインループだけが止まると最後の指令が出続けるため、IWDG
(`WATCHDOG_TIMEOUT_MS`) でリセットする。リセット中は出力ピンが Hi-Z になりコーストする。
HardFault でも 3 相出力を切ってからリセットを待つ。

## テストベクタ

`make -C tests` で検証される。

**受信** — 位置指令 0.5 rad / トルク上限 0.050 N・m:

```
AA BB 01 F4 32 26
```

`0x01F4` = 500 → 500 × 0.001 = 0.5 rad、`0x32` = 50 → 0.050 N・m。
CRC は byte1–4 (`BB 01 F4 32`) に対して `0x26`。

> フレーム仕様を変えると CRC の値も変わる。上位と MD は必ず同時に更新すること (片側だけだと全フレームが CRC エラーで落ちる)。

**送信** — status=過電流+動作中 / 42 degC / theta 1.0 rad / speed −12.34 rad/s /
iq 2.5 A / トルク上限 0.050 N・m:

```
AA 09 2A 27 10 FB 2E 09 C4 32 7C
```

CRC は byte1–9 に対して `0x7C`。
