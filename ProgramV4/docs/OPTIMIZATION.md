# ProgramV4 最適化メモ

FOCが動いたあとの「もっと良くする」作業の記録。着手順とその根拠。

## 大前提: 制御周期もPWM周波数も上げる必要はない

数字で確認したこと。

- 最高速度 `MAX_ANGULAR_SPEED = 150 rad/s` × `POLE_PAIRS = 7` = **電気角 167 Hz**
- 20 kHz PWM = **電気1周期あたり120サンプル**。FOCの定石 (10〜20サンプル) の10倍近くある
- 電流リプル `ΔI_pp ≈ Vdc / (4・L・fsw)` = 12 / (4 × 0.5m × 20k) ≈ **0.3 A_pp**。
  `MAX_CURRENT = 10 A` に対して3%なので、すでに問題になっていない

電流ループは PWM周期と1:1 (デューティは1周期に1回しか更新できない) なので、
速くするには PWM周波数ごと上げるしかない。しかし上げると:

1. スイッチング損失が `fsw` に比例して増える
2. **ローサイドシャントのサンプリング窓が絶対時間で縮む** →
   `MAX_DUTY` をさらに下げるしかなくなり、最高速度が落ちる

→ **20 kHz が最適点。上げない。**

## 7. エンコーダの継ぎ目が残りの律速

遅れ補償で連続的な角度ずれは消えたが、`emax` は変わらない。

| 速度 | emax [rad] (機械角) | 電気角 |
|---|---|---|
| 20 rad/s | 0.11 〜 0.18 | 44〜72° |
| 120 rad/s | 0.03 〜 0.19 | 12〜76° |
| 247 rad/s | 0.03 〜 0.24 | 12〜96° |

**ほぼ速度に依存しない** → 遅れではなく**校正の継ぎ目の段差**。
[bldc.h](../src/bldc/bldc.h) 自身のコメントの基準では「0.05rad を超えたら精度不足」。

実害は `Vd` ±0.3V、`Id` ±0.6A、`Iq` 0.03〜0.49 (目標0.30) のばらつき。
1回転に1回、電気角で最大96°飛ぶので、その瞬間 dq変換が崩れて Id と Iq が入れ替わる。

**根本対策 (I2CでAS5600のフィルタを速くする) は使えない。**
[FOC.md](FOC.md) のとおり CurcuitV4 は AS5600 の SDA/SCL が未接続でアナログ出力のみ。
→ V5 の基板課題。

ソフト側の候補:

1. **エンコーダ校正のやり直し** (スイッチを押しながら起動)。まず一番安い手
2. 飽和域を抜けたあとも数サンプル棄却を続け、センサ出力が整定してからPLLに戻す
3. 継ぎ目は機械角の固定位置に出るので、補正テーブルを持つ (大がかり)

## 2番の実測結果 (2026-07-29)

```
[PROF] irq 10.82/23.83us (CPU 21.6/47.7%)  cb 18.57us  周期  2.11-47.92us  n=40000
       内訳: PLL 4.06us  電流ループ 13.18/13.72us  外側 1.04us (n=1000)
```

この1行から3つ分かった。**どれも事前の予想になかった。**

### (a) 割り込みが 40 kHz で入っていた → 2b で修正済み

`n = 40000` (20000のはず)、周期が `2.11-47.92 µs` の2値。
ADC1のDMAは2変換なので**1変換目の完了でハーフ転送(HT)割り込みが立つ**。
`HAL_ADC_Start_DMA` が `XferHalfCpltCallback` を繋ぐので、中身が空の
`HAL_ADC_ConvHalfCpltCallback` を呼ぶためだけに毎回 1.04 µs 使っていた。

内訳の整合も取れる。TC側のコストを X、HT側を Y とすると
`(X+Y)/2 = 10.82` かつ `X ≈ cb 18.57 + HALのディスパッチ約2` なので **Y ≈ 1.04 µs**。
HT処理(1.04 µs)の途中でTCが立つため、TCの入口が 2.11 µs 後ろにずれていたのも辻褄が合う。

対策は [current_sense.c](../src/bldc/current_sense.c) で `__HAL_DMA_DISABLE_IT(hadc1.DMA_Handle, DMA_IT_HT)`。
`HAL_DMA_IRQHandler` のHT処理は `CCR` の HTIE を見てから走るので、これで発生しなくなる。

### (b) 本当のCPU使用率は 21.6% ではなく 43%

表示が「1回あたりの時間 × **想定** 20 kHz」で計算していたので、実レートが倍だったぶん
半分に見えていた。**想定周波数を使う計算は、想定が外れると静かに嘘をつく。**

→ 「区間内の合計サイクル数 ÷ 実経過時間」に変更し、実測レートも表示するようにした。

HT割り込みを止めた後の見込みは `20.6 µs × 20 kHz` = **CPU 約41%**。
最大 23.8 µs / 50 µs なので取りこぼしの危険は無いが、余裕たっぷりでもない。

### (c) ISRの時間は float の比較が食っている

`cb = 18.57 µs` = 1337 サイクル。内訳は PLL 4.06 + 電流ループ 13.18。
特に **PLL の 4.06 µs (292 サイクル)** は、やっている演算量に対して明らかに多い。

逆アセンブルして命令を数えると理由がはっきりする。

| | `vcmpe.f32` + `vmrs` | `vmul.f32` | `vadd/vsub` |
|---|---|---|---|
| コールバック全体 | **53組** | 28 | 8 |
| `BLDC_UpdateEncoder` | **20組** | 10 | 4 |

Cortex-M4F で float を比較すると `VCMP.F32` → `VMRS APSR_nzcv, FPSCR` の2命令が要る。
この `VMRS` は**FPUのフラグをコアのフラグに転送する**命令で、
パイプラインが揃うまで待つため 1命令なのに実質 4〜6 サイクルかかる。
分岐まで含めると **1回の比較で 8〜10 サイクル**。乗算・加算 (1サイクル) の10倍。

53組 × 約9サイクル ≈ **480サイクル ≈ 6.6 µs**。`cb` の3分の1がこれ。

犯人は [mymath.h](../lib/mymath/mymath.h) の2つのマクロ。

```c
#define Abs(x) ((x) > 0 ? (x) : -(x))                    // → VCMP + VMRS + 分岐
#define Constrain(amt, low, high) ((amt) < (low) ? ... )  // → その2回分
```

`Abs()` は float なら **`VABS.F32` 1命令 (1サイクル、フラグ転送なし)** で済む。
`__builtin_fabsf()` がちょうどこれにコンパイルされる。**10倍の差**。

## 2c でやったこと (2026-07-29)

### 1. `Abs()` を float では `VABS.F32` に

[mymath.h](../lib/mymath/mymath.h) で C11 の `_Generic` を使い、型ごとに振り分けた。

```c
static inline float AbsF(float x) { return __builtin_fabsf(x); }
#define Abs(x) _Generic((x), float: AbsF, double: AbsD, default: AbsL)(x)
```

`((x) > 0 ? (x) : -(x))` は float だと VCMP + VMRS + 分岐で8〜10サイクル。
`VABS.F32` なら**1サイクル**。マクロの2回展開問題 (`Abs(*p++)` が壊れる) も消える。
既存の使用箇所は全部 float だったので、`default` 側は将来のための保険。

### 2. `FOC_SinCos` の前の正規化を削除

三角関数は内部で `x/2π` の小数部を取るので**入力範囲は任意でよい**。
`mech_theta × 7` (最大44 rad) を while ループで引き算していたのは丸ごと無駄だった。
表示用の正規化は `BLDC_GetElecTheta` 側に移した。

### 3. `FOC_SinCos` を自前実装に (sin/cos を1回の縮約で)

`arm_sin_f32` と `arm_cos_f32` を別々に呼ぶと、同じ引数に対して範囲縮約が2回走り、
関数呼び出しも2回になる。`cos(θ) = sin(θ + π/2)` で π/2 はテーブル512点の**ちょうど128点**
ぶんなので、縮約と補間係数を1回で済ませて両方引ける。

数値検証 (host で 4.4M 点、`[0, 44) rad`):

| | 真値 (libm) との誤差 | 旧 CMSIS 実装との差 |
|---|---|---|
| sin | 1.91e-05 | 5.96e-08 |
| cos | 1.91e-05 | 1.50e-06 |

1.9e-5 は512点テーブル + 線形補間の量子化限界そのもので、CMSIS と同等。
cos が旧実装と 1.5e-6 違うのは、CMSIS が `+0.25` を float で足してから小数部を取るのに対し、
こちらは**整数のインデックスを128ずらす**ため。ずらしが厳密なぶん新実装のほうが正確。
どちらにせよエンコーダの分解能 (1.5 mrad) の1000分の1なので無関係。
`sin²+cos²-1` の最大は 3.8e-05、負の入力・2πの境界・44 rad も確認済み。

### 4. デューティのクランプを整数比較に

```c
static inline uint32_t BLDC_DutyToCcr(float duty) {
  int32_t ccr = (int32_t)(duty * PWM_ARR);
  if (ccr < CCR_MIN) ccr = CCR_MIN;
  if (ccr > CCR_MAX) ccr = CCR_MAX;
  return (uint32_t)ccr;
}
```

整数の比較はコアのフラグを直接使うので1サイクル。3相で6回あるので効く。
**安全性も上がる**: ARMの `VCVT` は NaN を 0 に、範囲外を飽和させるので、
変換してから整数でクランプすれば入力が何であれ必ず範囲に収まる。
float のまま比較すると NaN は「どの比較も偽」ですり抜けてしまっていた。

## 2d (見送り): ホットパスを CCM RAM で実行

**やらない。33.8% / ピーク 19.85 µs で余裕が足りているため。**
最適化は「足りるまで」で止めるのが正しい。以下は将来また詰まったときのためのメモ。

### まだ残っている無駄: HALのディスパッチ 約1.5 µs

`irq 16.89` − `cb 14.68` = **2.21 µs**。ここから計測自身のぶん (IRQ入口の
`ProfilePeriod_Mark` + `Profile_Begin`/`End` で約0.67 µs) を引くと、
`DMA1_Channel1_IRQHandler` → `HAL_DMA_IRQHandler` → `ADC_DMAConvCplt` →
コールバック という HAL の経路だけで **約1.5 µs (CPUの3%)** 使っている。

DMA割り込みフラグを直接クリアして制御関数を呼ぶベアメタルのハンドラに置き換えれば消せる。
必要になったらここから。

### フラッシュのウェイトステート

命令数と比較コストから積み上げた見積もりより実測が大きい。差はおそらくこれ。

- 72 MHz なので `FLASH_LATENCY_2` (2ウェイト)。プリフェッチバッファは有効
  (`PREFETCH_ENABLE 1` を確認済み) だが、**分岐するたびにバッファが無効になって詰め直し**が要る。
  ホットパスには分岐が40個近くある

- 72 MHz なので `FLASH_LATENCY_2` (2ウェイト)。プリフェッチバッファは有効 (`PREFETCH_ENABLE 1`) だが、
  **分岐するたびにバッファが無効になって詰め直し**が要る。ホットパスには分岐が40個近くある
- STM32F303 の CCM SRAM (4 KB) は **I-bus に繋がっていて命令フェッチができる**。
  ここに置けば 0 ウェイトで走る (F4 の CCM は D-bus 専用なので不可。F3 の利点)

やるなら:

1. `startup_stm32f303x8.s` に `.ccmram` を FLASH (`_siccmram`) から CCM (`_sccmram`〜`_eccmram`) へ
   コピーするループを追加する。**リンカスクリプトの側はすでに用意されている** ([STM32F303XX_FLASH.ld](../STM32F303XX_FLASH.ld) の
   `.ccmram : { ... } >CCMRAM AT> FLASH`)。startup 側のコピー処理だけが無い
2. ホットパスの関数に `__attribute__((section(".ccmram")))` を付ける

サイズが厳しい。コールバック 2228 B + `BLDC_UpdateEncoder` 608 B + `FOC_SVPWM` 168 B
+ `FOC_LimitVoltageVector` 76 B + `CurrentSense_Read` 108 B ≈ **3.2 KB / 4 KB**。
HAL のディスパッチまで入れると溢れるので、上記のベアメタル化とセットになる。

### 3. センター揃えPWM ✅ 完了 (2026-07-29)

実装内容:

| | 変更前 | 変更後 |
|---|---|---|
| カウントモード | エッジ揃え UP | **センター揃え** (`CENTERALIGNED1`) |
| `PWM_ARR` | 3599 (`72M/(ARR+1)`) | **1800** (`72M/(2×ARR)`) |
| デューティ | `CCR/(ARR+1)` | **`CCR/ARR`** |
| ADCトリガ | `CCR4 = 3200` (区間の端) | **`CCR4 = ARR-50 = 1750`** (区間の中央) |
| `MAX_DUTY` | 0.80 | **0.88** |
| 変調率 | 0.346 | **0.439** (+27%) |

タイマ設定は `tim.c` ではなく `BLDC_Init` で上書きしている。`tim.c` は CubeMX の
再生成で消えるため (BDTR の OSSI や ADC1 の再初期化と同じ考え方)。

**副次的な効果のほうが重要かもしれない**: 低側ON区間の中央でサンプリングするので、
取れる値が「その瞬間の電流」ではなく**三角波リプルの平均 = その周期の平均電流**になった。
これは `CURRENT_LPF_COEF` を緩められるということ (次の4番の前提)。

設定の整合は `config.h` の `_Static_assert` 3本で検査している。
`MAX_DUTY_CCR` / `CURRENT_SENSE_TRIG_ADVANCE` / `CURRENT_SENSE_ACQ_COUNTS` /
`PWM_ARR` のどれか1つを勘で触るとビルドが落ちる。
(意図的に壊して両方の条件が発火することは確認済み)

なお `MAX_DUTY` は float ではなく `MAX_DUTY_CCR`(整数) を正として定義している。
`_Static_assert` は整数定数式しか受け付けず、`(int)(0.88f * 1800)` は
整数定数式にならないため。ハードウェアが実際に比較するのもカウント数なので、
こちらのほうが本質でもある。

#### 残っている改善余地

`CURRENT_SENSE_SETTLING_COUNTS = 144` (2.0 µs) は**データシートからの保守的な見積もり**。
INA181A1 の帯域 350kHz から τ = 455ns、1%整定 = 4.6τ = 2.1µs と計算した値で、
オシロで実測したものではない。実測すれば 0.92 (変調率 0.485, +40%) まで見込める。

**オシロが無くても ADC 自体で測れる** (未実施):

1. 開ループでロータを固定し、一定の直流電流を流す
2. `TIM1->CCR4` を低側ON直後から頂点までスイープ
3. 各点で電流を平均して記録
4. 低側ON区間の中では真の電流は一定なので、**読み値が変化している間は未整定**。
   平らになった点が整定完了

デューティ 0.65/0.425/0.425 で駆動すればU相とV相で低側ONの時刻が違うので、
1回のスイープで2つの独立した測定が取れて相互検証にもなる。
オシロと違い、シャント → INA181 → ADCサンプルホールドという
**制御ループが実際に通る経路そのもの**を測れるのが利点。

### 3の設計メモ (当時)

いまの `MAX_DUTY = 0.80` が全体の一番の制約になっている。

```
MAX_MODULATION_RATIO = (0.80 - 0.5) × 1.1547 = 0.346
SVPWM の理論上限                              = 0.577  (= 1/√3)
```

**母線電圧の利用率が理論値の60%しかない。** 12 V なら相電圧振幅 4.16 V しか出せず、
本来出せる 6.93 V に届いていない = 最高速度が約40%削られている。

原因はエッジ揃えPWM + 周期末尾サンプリング。低側ON区間 `[CCR, ARR]` の
**後ろ側しか使えない**ので、サンプリング点より手前のデューティしか許されない。

対策:

- [tim.c](../Core/Src/tim.c) の `CounterMode` を `TIM_COUNTERMODE_CENTERALIGNED1`、
  ARR = 1799 (アップダウンで 72 MHz / (2 × 1800) = 20 kHz)
- PWM1モードなら高側ONが CNT=0 中心、**低側ONがカウンタ頂点 (CNT=ARR) 中心**になる
- CCR4 = ARR でトリガすれば**低側ON窓のちょうど中央**でサンプリングできる

窓が周期の両側に分散するので `MAX_DUTY ≒ 0.90〜0.93` まで引ける。
変調率 0.346 → 0.46〜0.50。

おまけ: 3相の立ち上がりが同時でなくなるのでリプルとEMIが下がる。
さらに、低側ON窓の中央のサンプル = **1周期の平均電流そのもの**になるので、4番の前提が整う。

### 4. 電流ループの帯域 🔶 測定待ち (2026-07-29)

#### 済: LPFを緩めた (0.25 → 0.5)

`CURRENT_LPF_COEF` のカットオフ `fc = fs × -ln(1-a) / 2π` は **916 Hz → 2206 Hz**。

3番でセンター揃えにしたので、1サンプルがそのまま「その周期の平均電流」になった。
リプルを均すためのフィルタはもう要らない。残る役割は単発ノイズの除去だけで、
量子化は 0.0081 A/LSB (7Aに対して0.1%) なので強くかける理由が薄い。
一方でフィルタの位相遅れは帯域を直接制限していた。
**この変更は位相余裕を増やす方向なので単体で安全。**

#### 実測でわかったこと (1回目): 応答が1次系ではなかった

```
0.15  0.944 ↑速い立ち上がり
0.20  1.045 ← 山
0.40  0.735 ← 谷 (30%落ちる)      周期0.4ms ≒ 2.5kHz のリンギング
0.60  0.887 ← 山
1.00  0.888 ┐
3.00  0.976 │ 時定数 1.3ms で ゆっくり 1.0 へ這い上がる長い尾
5.00  0.999 ┘
```

**速いモードと遅いモードの2つに割れている。** 尾はきれいな指数で、1msごとの残差が
0.112 → 0.052 → 0.024 → 0.012 (比 0.46 一定) から **時定数 1.30ms = 768 rad/s**。

閉ループの特性方程式 `L·s² + (R+Kp)·s + Ki` の2極について

```
p_fast + p_slow = (R + Kp) / L
p_fast × p_slow = Ki / L
```

から逆算すると **L ≈ 0.10〜0.18 mH、R ≈ 0.3 Ω**、つまり `R/L ≈ 2000〜3000 rad/s`。
一方 PIのゼロ点は `Ki/Kp = 1000 rad/s` で**3倍ずれていた**。

> 極とゼロが打ち消し合っていないから、応答が2つの時定数に割れる。

リンギングのほうは、`Kp/L ≈ 1000Hz` の開ループ帯域に 1.5周期(75µs)の演算遅れが
効いた離散時間系の振動。**L は小さい側で、事前に懸念した「上げてはいけない」ケースだった。**

#### `CURRENT_BW_SCALE` は破棄した

KpとKiを同じ倍率で動かす方式は **`Ki/Kp = R/L` が既に成り立っている前提**だった。
成り立っていないので、倍率をかけても「ずれた比を保ったまま」動くだけ。
実際 SCALE=0.45 を適用すると遅い極が 768 → 403 rad/s になり、**尾がもっと長くなる**。

必要なのは倍率ではなく**比の修正**で、そのためには L と R の値が要る。
`MOTOR_L` / `MOTOR_R` / `CURRENT_BW_HZ` から Kp, Ki を導く形に変更した。

#### 未: ゲインの倍率は実測してから決める

`Kp` を上げてよいかは **L 次第で結論が正反対になる**:

| もし L が | いまの帯域 `Kp/(2πL)` | 判断 |
|---|---|---|
| 0.5 mH | 240 Hz | 3倍にすべき |
| 0.15 mH | 796 Hz | **上げてはいけない** (位相余裕が一桁に落ちて発振) |

L が分からないので勘で上げるのはコインの裏表。ただしここに使える性質がある:

> **KpとKiを同じ倍率で動かせば、LとRを知らないまま帯域だけを比例で動かせる。**
> PIのゼロ点がプラントの極を打ち消す関係 (`Ki/Kp = R/L`) が倍率で保たれるため。
> いまの `Ki/Kp = 1000 rad/s` が、このモータの `R/L` の推定値。

必要なのは「いまの帯域が何Hzか」という**1つの数字だけ**。そこで `CURRENT_BW_SCALE`
を導入し、既定を 1.0 (＝従来と同一) にして、実測してから決める形にした。

帯域の上限はプラントではなく**位相遅れ**が決める:

```
1.5周期の演算遅れ   : ω_bw × 1.5 × 50µs   (700Hzで 18.9°)
電流LPF (fc=2.2kHz) : atan(f_bw / 2206)    (700Hzで 17.6°)
→ 700Hz で位相余裕 約53°。これが現実的な上限
```

(6番の演算遅れ補償を入れれば、この上限はもう少し上がる)

#### 測定方法: d軸ステップ応答 (`MEASURE_CURRENT_STEP`)

**d軸に電流ステップを入れて Id の応答を20kHzで記録する。**

d軸はロータの磁束方向なので**トルクが出ずロータが動かない**。逆起電力も負荷変動も
混ざらない「純粋な電気的応答」だけが取れる。表面磁石型(SPM)は Ld = Lq でPIゲインも
共通なので、結果はq軸にそのまま当てはまる。オシロは要らない
(制御ループ自身が20kHzでサンプリングしているので分解能50µsで記録できる)。

出力から `いまの帯域` と `700Hzにするための CURRENT_BW_SCALE` が直接読める。

**注意: 63%到達点は必ず線形補間すること。** 「最初に閾値を超えたサンプル」を
そのまま使うと τ を切り上げる方向に読み、帯域を系統的に**過小評価**する。
合成波形で検証した結果:

| 真の帯域 | 補間なし | 補間あり |
|---|---|---|
| 240 Hz | 227 Hz (-5.3%) | 240 Hz (0.0%) |
| 700 Hz | 637 Hz (-9.1%) | 696 Hz (-0.6%) |
| 1000 Hz | 796 Hz (-20.4%) | 992 Hz (-0.8%) |
| 1500 Hz | 1061 Hz (-29.3%) | 1481 Hz (-1.3%) |

20kHzサンプリングの原理的な限界として、63%到達が3サンプルを切ると誤差が増える。
その場合は警告を出すようにしてある。

**さらに: 63%点だけを見て時定数を語ってはいけない。** 1回目の測定がまさにそれで、
2つの時定数に割れた応答の速いほうだけを拾って「1570Hz」と報告してしまった。
いまは 1τ / 2τ / 3τ で理想の 63.2 / 86.5 / 95.0% と比べ、10%以上ずれたら
**「1次系になっていない」と表示して帯域の値を出さない**ようにしてある。
実機で取れた波形を入れて、正しく弾くことを確認済み:

| 入力 | 1τ | 2τ | 3τ | 判定 |
|---|---|---|---|---|
| 実機の波形 (1回目) | 62% | **104%** | 84% | **1次系でない** ✓ |
| 理想1次系 240Hz | 62% | 86% | 95% | 1次系 ✓ |
| 理想1次系 700Hz | 59% | 86% | 94% | 1次系 ✓ |
| 理想1次系 1500Hz | 61% | 85% | 94% | 1次系 ✓ |

#### 同定方法: 電圧ステップ (`MEASURE_MOTOR_RL`)

閉ループのステップ応答から極を逆算する方法は、リンギングのせいで精度が出ない。
**PIをバイパスして Vd を直接与えれば、制御器が挟まらないので応答は素の1次系
(時定数 `L/R`) になり、モデルの仮定が要らない。**

```
定常値から   R = V / I_ss
63%到達から  τ = L/R  →  L = τ·R
```

**電圧は2点 (V と 2V) 振って差を取る。** デッドタイム (278ns = 母線電圧の0.56%
= 12Vで約0.067V) のぶん実際にモータへ加わる電圧は指令より一定量小さい。
この誤差は電圧指令の大きさによらずほぼ一定なので `R = (V2-V1)/(I2-I1)` で消える。

| | R | 誤差 | L |
|---|---|---|---|
| 真値 | 0.3000 Ω | — | 120.0 µH |
| 1点法 `V2/I2` | 0.3274 Ω | **+9.1%** | 131.0 µH |
| 2点法 `(V2-V1)/(I2-I1)` | 0.3000 Ω | **-0.0%** | 120.0 µH |

開ループなので電流を制限するものが他に無い。`MOTOR_RL_ABORT_AMPS` を超えたら
ISR内で即座に電圧を切る安全弁を入れてある。

##### 測定したτから L/R 以外の遅れを引くこと

63%到達時間には `L/R` 以外の遅れが2つ混ざっている。引かないと **L を4割過大評価する**。
`Kp = L·ω_bw` なので、そのぶん実際の帯域が設計値を超えて位相余裕が削られる。

| 遅れ | 大きさ | 理由 |
|---|---|---|
| 電流LPF | `-Ts/ln(1-a)` = **72 µs** | `svc.id` はフィルタ後の電流から計算される |
| 半周期 | **25 µs** | CCRはプリロード付き → 次の周期の頭から効く。電流を拾うのは低側ON区間の中央。よってサンプル n の実時間は `(n-0.5)·Ts` |

LPFの72µs は `L/R` (約200µs) の3割を超える。無視できない。合成波形での検証:

| 真の L | 補正なし | 補正あり |
|---|---|---|
| 25 µH | 42.0 µH (+67.9%) | 23.2 µH (-7.0%) |
| 45 µH | 61.6 µH (**+36.9%**) | 42.9 µH (**-4.7%**) |
| 85 µH | 100.8 µH (+18.5%) | 82.0 µH (-3.5%) |

**L が小さいほど誤差が効く。** このモータはまさにその領域だった。

#### 実測結果 (2026-07-29)

```
V=0.400V → 定常 1.778A, 63%到達 0.311ms
V=0.800V → 定常 3.852A, 63%到達 0.295ms
→ MOTOR_R = 0.1928 Ω   (1点法なら 0.2077。差 7.7% がデッドタイム誤差)
→ τ 0.295ms − LPF 0.072ms − 半周期 0.025ms = 0.198ms
→ MOTOR_L = 38 µH   (補正なしなら 57 µH)
→ R/L = 5074 rad/s
```

デッドタイム損は `0.8 - 3.852×0.1928 = 0.057V` と逆算でき、事前見積もり (0.067V) と一致。
2点法が効いていることの裏づけになっている。

**`Ki/Kp` は 1000 のはずが実際の `R/L` は 5074 で、5倍ずれていた。**
新しいゲインは `Kp = 0.203` (旧 0.75 の約1/4)、`Ki = 1030` (旧 750)。
つまり **Kp は下げるのが正解だった**。最初の見立てどおり2〜3倍にしていたら
`Kp/L` が 9 kHz を超えて確実に発振していた。

#### 結果

| | 前 (Kp=0.75, Ki=750) | 後 (Kp=0.203, Ki=1030) |
|---|---|---|
| 95%整定 | 2.1 ms | **0.50 ms** |
| 実測帯域 | (2つに割れていて定義できない) | **714 Hz** |
| 挙動 | 1.045まで行き0.735まで落ちる | 単調、オーバーシュート 1.7% |
| 長い尾 | 時定数1.3msで這い上がる | 無し |

**整定が4.2倍速くなり、±15%の振れが消えた。**

#### 判定は 3τ を主役にすること

「1次系かどうか」の判定を最大ずれ ±10% で見ていたが、実測が +9% と閾値ギリギリになった。
物理的に意味のある指標に変更:

| | 2τ のずれ | 3τ のずれ | 意味 |
|---|---|---|---|
| 壊れていたとき | +16% | **-13%** | 3τでも95%に届かない = **遅い尾が残っている** |
| 直したあと | +8% | **+4%** | 尾は無い |
| 理想1次系 | 0% | 0% | — |

**3τ が 95% に届かない**のが極零不一致の症状。
一方 2τ が理想より高めに出るのは、ループ内の遅れ (電流LPFと演算遅れ) で立ち上がりが
後ろにずれ、そのぶん τ を長めに読むため。遅れは避けられないので異常ではない。
判定は `3τ < -8%` を主、`2τ > +20%` を従とした。-13% と +4% の間は十分に開いている。

#### 検査コードのインデックスも補間すること

τ は整数サンプルとは限らない (63%点自体を補間で求めているので当然)。
`(uint16_t)(k63f * m)` と切り捨てると交差点の**手前**の値を拾い、
**1τ が定義上63%のはずなのに51%**と出る。しかも誤差の大きさが τ の小数部に
依存するので、同じ品質の応答でも通ったり落ちたりして判定として成立しない。

実際 `k63f=6.08` のときは通り、`k63f=4.96` のときに誤って落ちた。
63%点の検出で補間を入れながら、その直後の検査で同じ罠に落ちていた。

#### 設計値と実測値の乖離

`CURRENT_BW_HZ = 700` で実測 570Hz (補正後)。`ω_bw = Kp/L` の式が
理想的な極零相殺と遅れ0を前提にしているのに対し、実際のループには電流LPFと
演算遅れが入るため、実測は設計値より2〜3割低く出る。比率で割り戻して
`CURRENT_BW_HZ = 850` にしてある (実測 690Hz 前後の見込み)。

**この値は設計パラメータであって実測帯域ではない**ことに注意。
上げるときは必ず `MEASURE_CURRENT_STEP` で確認すること。

### 5. 逆起電力・dq干渉フィードフォワード 🔶 ψm測定待ち (2026-07-29)

`Vd -= ω_e·L·Iq`、`Vq += ω_e·L·Id + ω_e·ψm` を電流PIの出力に足す。
`L` は4番で実測済みなので dq干渉の2項は即使える。`ψm` は `MEASURE_MOTOR_PSI` で同定。

#### モデルで検証した効果

実測の `L=38µH, R=0.1928Ω, Kp=0.2029, Ki=1030` で dq電圧方程式を数値積分し、
Iq を 2A ステップさせたときの 95% 到達時間:

| 機械角速度 | FF無し | **FF 正しい** | FF 符号ミス |
|---|---|---|---|
| 0 rad/s | 0.55 ms | 0.55 ms | 0.55 ms |
| 80 rad/s | 1.35 ms | **0.55 ms** | 1.55 ms |
| 160 rad/s | 1.55 ms | **0.55 ms** | **破綻** (10.3A偏差、指令に到達せず) |

**正しいFFでは応答が速度に依存しなくなる。** 積分項も 0.39V のまま
(FF無しは160rad/sで 4.87V)。電圧の余裕を積分で食い潰さないので飽和しにくい。

効くのは「速さ」と「余裕」であって定常精度ではない。積分がある以上、
時間さえあれば定常偏差はどちらでも0になる。

#### 符号を間違えると外乱が倍になる

FFの符号を反転すると、打ち消すはずの項が二重に効く:

```
正: diq/dt = (PI + ω_e·L·Id + ω_e·ψm − R·Iq − ω_e·L·Id − ω_e·ψm)/L = (PI − R·Iq)/L  ← 相殺
誤: diq/dt = (PI − ω_e·L·Id − ω_e·ψm − R·Iq − ω_e·L·Id − ω_e·ψm)/L                  ← 倍増
```

実機で確認するときは `STATUS_PRINT` の `Vq(FF...)` を見る。
**FFがVqと同符号で、速度とともにVqの大半を占めるようになっていれば正しい。**
逆符号で出ていたら実装ミス。

#### ψm の同定 (`MEASURE_MOTOR_PSI`)

一定速度の定常状態では `dIq/dt = 0` なので `Vq = R·Iq + ω_e·ψm`。
L・R のときと同じく2点で測って差を取り、一定オフセットを消す:

```
ψm = ((Vq2 − Vq1) − R(Iq2 − Iq1)) / (ω_e2 − ω_e1)
```

**この測定だけはロータが実際に回る。** 開始前に3秒のカウントダウンが入る。

FFが有効なままでも測定は成立する。定常状態で必要な `Vq` の総量は `ψm` の真値だけで
決まり、それをPIとFFのどちらが出すかは結果に影響しない (FFが足りなければPIが埋め、
出しすぎればPIが引く)。

#### 実測結果 (2026-07-29)

```
40 rad/s → ω_e 280, Vq 0.824V, Iq 0.221A
80 rad/s → ω_e 560, Vq 1.356V, Iq 0.287A
→ MOTOR_PSI = 0.001854 Wb   (1点法なら 0.002322 = **+25%**)
```

検算 (すべて小型モータとして整合):

- 無負荷到達速度 `V_lim/(ψm·P)` = **406 rad/s** (12V, 3878rpm ≒ Kv 323)
- トルク定数 `1.5·P·ψm` = **0.0195 N·m/A**
- 保持電流 40rad/s で 0.221A → 80rad/s で 0.287A (摩擦が速度とともに増える)

#### 副産物: Vq に 0.262V の一定オフセットがある

2点の実測値から逆算すると、両点でぴったり同じオフセットが出る:

```
40 rad/s: 0.824 = offset + 0.1928×0.221 + 280×0.001854 → offset = 0.262V
80 rad/s: 1.356 = offset + 0.1928×0.287 + 560×0.001854 → offset = 0.262V
```

「一定オフセット」モデルが正しいことの裏づけ。
(試しに「Rが違う」モデルで解くと `R=1.88Ω` となり、実測 0.193Ω の10倍で不合理)

正体はデッドタイムによる電圧損。**40 rad/s では Vq の32%を占める。**
しかも電流の向きで符号が反転するので、Iq がゼロを跨ぐたびに 0.52V の飛びが出る。
→ **6番のデッドタイム補償の重要度が当初の見積もりより上がった。**

#### FF を入れて見えた別問題: 角度が速度に比例して遅れていた

FF自体は正しく効いていた (182 rad/s で FF 2.37V、理論値 ω_e·ψm = 2.362V と一致)。
しかし **PIがFFを打ち消す方向に強く効いていた** (Vq 0.45V に対し FF 2.37V → PI −1.92V)。
これは推定角がずれているときの典型的な症状。

`Vd` を表示に追加して2速度で比較すると決定的だった:

| 速度 | Vd 実測 | 角度が正しければ `−ω_e·L·Iq` |
|---|---|---|
| 20 rad/s | −0.03 V | −0.001 V |
| **120 rad/s** | **−1.25 V** | **−0.011 V** |

`Vd` と `Vq` の2式から `ψm` と `δ` を同時に解くと:

```
Vd = R·Id − ω_e·L·Iq − ω_e·ψm·sin δ
Vq = R·Iq + ω_e·L·Id + ω_e·ψm·cos δ
```

| 速度 | δ (電気角) | 解けた ψm |
|---|---|---|
| 20 rad/s | 6.2° | 0.00217 Wb |
| 120 rad/s | 49.4° | 0.00192 Wb |

ψm が両速度でほぼ一致するのでこの解き方は妥当 (実測 0.001854 とも近い)。
**δ が速度にほぼ比例** → `δ = −2.4° + 0.432°/(rad/s) × ω_mech` → **一定の時間遅れ 1.08 ms**。

内訳: 演算遅れは 1.5周期 = 0.075ms しかない。**残る約1.0msはセンサ側 (AS5600の内部フィルタ)**。
PLLは犯人ではない。2次PLL (ζ=1) は等速回転に対して定常位相遅れがゼロになる設計なので、
速度比例の遅れは出さない。

→ `ANGLE_DELAY_S` で推定角を `ω̂ × t` 進めて補償する (6番の演算遅れ補償と同じ形。
定数が 0.075ms から 1.08ms に増えるだけ)。**FFは角度が正しいときにしか本来の効果を
出さない**ので、これを直すまで5番の利得は出ない。

##### 補償の結果 (実測)

| | 補償前 (120 rad/s) | 補償後 (247 rad/s) |
|---|---|---|
| `Vd` | **−1.25 V** | **平均 +0.01 V** (±0.3 ばらつき) |

速度が2倍なので補償なしなら −2.5V 程度になっていたはず。**ゼロ中心になった。**

電圧の収支も閉じた:

```
247 rad/s, ω_e = 1733
必要な Vq = R·Iq + ω_e·ψm = 0.1928×0.36 + 3.21 = 3.28 V
実測 Vq                                        = 3.33 V   差 0.05V
```

(補償前は「Vq 0.45V に対し必要 2.60V」で 2.1V 合わなかった)

**体感でも明確に速くなった。** 補償前は電気角が49°ずれていて `cos(49°)=0.66` しか
トルクにならず残りはd軸に無駄流れしていた。いまは全部がトルクになる。
`0.3A` で 247 rad/s (補償前は `1.0A` で 182 rad/s)。

##### ψm は再測不要だった

角度が正しくなったので直接計算できる:

```
ψm = (Vq − R·Iq)/ω_e = (3.335 − 0.069)/1733 = 0.001884 Wb
```

config の 0.001854 との差は **1.6%**。「δの影響で過小評価されているのでは」は杞憂で、
2点法がδの影響下でも十分な精度を出していた。

#### 表示の設計ミスを1つ修正

`→ 目標に合わせるなら CURRENT_BW_HZ = 949` は追いかけっこになる提案だった。
`CURRENT_BW_HZ` は設計パラメータで実測はそれより2割低く出ると分かっているのに、
実測を設計値に合わせようとしていた。949にすれば次は1060を要求する循環。

「実際に達成したい帯域」を `CURRENT_BW_TARGET_HZ` として分離した。

### (旧メモ) 逆起電力フィードフォワード

いまは Vd/Vq をPIだけで作っている。モータの電圧方程式には干渉項がある:

```
Vd = R・Id + L・dId/dt − ω_e・L・Iq
Vq = R・Iq + L・dIq/dt + ω_e・L・Id + ω_e・ψ_m
```

`ω_e・ψ_m` は速度に比例して大きくなる**外乱**で、いまはPIの積分項が追いかけている。
掛け算3回足すだけで消せる。`ψ_m` は無負荷で回して逆起電力から同定する。

### 6. その他

- **1.5周期遅れ補償**: サンプル k の角度で計算した電圧が効くのは k+1 の中央 =
  75 µs 遅れ。逆Park用の角度だけ `+ ω_e × 1.5 × CURRENT_LOOP_DT` 進める
- **位置制御のD項**: 誤差の微分 + 35 Hz LPF をやめ、PLLの ω̂ をそのまま使う
  (`d_term = -kd * angular_speed`)。微分ノイズもLPF遅れも消える
- **デッドタイム補償**: DTG = 20 → 278 ns (周期の0.56%)。低速トルクリプルの原因
- **ADC2 のサンプリング時間**: [adc.c](../Core/Src/adc.c) の rank3 (TEMP) に
  `SamplingTime` を設定し直していないので rank2 の 601.5 cycles が残っている。
  スキャン1周が 74 + 614 + 614 = 1302 cycle = **18.1 µs**。
  ただしPLLの帯域が 32 Hz なのでジッタはほぼ平滑される。優先度は低い

## プロファイラの使い方 (2番の成果物)

`config.h` の `PROFILE_ISR` で有効化する。実体は [lib/profile/profile.h](../lib/profile/profile.h)。

```c
#define PROFILE_ISR 2              // 0:無効  1:全体のみ  2:内訳も
#define PROFILE_PRINT_INTERVAL_S 1.0f
```

DWT (Cortex-M4のデバッグユニット) の `CYCCNT` を区間の前後で読んで引き算する。
コアクロックをそのまま数えているので分解能は 1 サイクル = 13.9 ns。
デバッガを繋がなくても `DEMCR.TRCENA` をソフトで立てれば動く。

GPIOトグル + オシロと違い、**最大値と平均を長時間ぶん積算できる**のが利点。
「たまに1回だけ長い」を捕まえられる。

### 出力例

```
BLDC: プロファイル有効 (PROFILE_ISR=2) 計測オーバーヘッド 11 cycle/区間 (0.153us)
[PROF] irq  X.XX/ X.XXus  CPU XX.X%  rate 20.00kHz  cb  X.XXus  周期 50.00-50.00us
       内訳: PLL X.XXus  電流ループ X.XX/X.XXus  外側 X.XXus (1.00kHz)
```

### 読みかた

| 項目 | 意味 |
|---|---|
| `irq` 平均/最大 | 割り込みハンドラ全体 (HALのディスパッチ込み) |
| `CPU` | 合計サイクル数 ÷ **実経過時間**。想定周波数を使わないので嘘をつかない |
| `rate` | **実測した**割り込み頻度。20.00 kHz でなければ何かがおかしい |
| `cb` | `HAL_ADC_ConvCpltCallback` の中身だけ。`irq - cb` が **HALのオーバーヘッド** |
| `周期` min-max | 50.00 µs から外れていたらADCトリガか割り込み優先度を疑う |

判断の目安:

- **`rate` が 20.00 kHz でない** → 想定外の割り込み源がある。他の全部の数字が意味を失う
  (実際これで DMA のハーフ転送割り込みを見つけた。上の (a) 参照)
- **`irq` の最大が 50 µs に近い** → 処理を足す余裕は無い。まず減らす
- **`irq - cb` が大きい** (数µs) → `DMA1_Channel1_IRQHandler` を
  HALを通さないベアメタル実装 (DMA割り込みフラグをクリアして直接制御関数を呼ぶ) に
  置き換える価値がある
- **`周期` の max が 50 µs を大きく超える** → 1回取りこぼしている。致命的
- **どこかが不自然に重い** → 逆アセンブルして命令を数えるのが早い。
  `objdump -d` して `vcmpe.f32`/`vmrs` の数を見ること (上の (c) 参照)

### 注意

- 計測自身のコストは起動時に**実測して表示される**。この値を知らないと
  出てきた数字のどこまでが本当の処理時間か判断できない
- `PROFILE_ISR = 2` は計測点が5箇所になるので `irq` が 0.5〜1 µs 水増しされる。
  **内訳を見るのは 2、CPU使用率の正確な値が欲しいときは 1** と使い分ける
- 表示は `printf` (USART1, 250000 baud, ブロッキング) なのでメインループだけが待つ。
  制御ループは割り込み優先度0なので影響を受けない
- 測り終わったら `PROFILE_ISR = 0` に戻すこと。計測コードごと消える
